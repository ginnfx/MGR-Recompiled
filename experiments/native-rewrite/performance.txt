M1: XDK native memory-oriented math
  826CBFB8: float array -> packed 16-bit array
    Previous: per-element guest stack staging, VMX permutation/packing, FPCR
    writes, register-bank round trips. Native: direct big-endian integer
    conversion, one FP mode transition at function exit, forward alias order.
    Preserve generated cutoff 65504, truncation, underflow, signed zeros and
    NaN/overflow saturation. This is not an IEEE-half conversion substitution.
  826CC010: packed array -> float array
    Previous: per-element VMX unpack and guest stack staging. Native: direct
    exponent rebiasing, exponent-zero flush, big-endian store, exit FP mode.
    Exponent 31 remains finite, matching the generated implementation.
  826CC0E0: vector normal transform
    Previous: emulated VMX registers with repeated load/permute/splat operations.
    Native: host vector/matrix row algebra using ARM NEON with identical
    multiplication/addition order, FP flush and no fused contraction.
    Initial scalar reconstruction failed NaN payload/sign parity and was
    slower through dispatch. Replaced by native SIMD; no ARM NaN fallback needed.
  826CC160: matrix transpose
    Previous: guest ABI save/restore, VMX load/merge/permute and scalar stores.
    Native: snapshot a typed 4x4 matrix, transpose its raw words; preserves
    NaNs and signed zeros without FP arithmetic; supports overlapping matrices.

  Boundary contract: leave guest return pointer and nonvolatile registers intact.
  Keep original __imp__ implementations linked. Physical aliases, MMIO,
  wrapping ranges, unaligned output-word layouts and array/transpose aliases
  with guest stack scratch retain the original implementation.
  MGR_NATIVE_MATH=0 restores originals; MGR_NATIVE_MATH_VERIFY=1 checks live
  transform and transpose outputs. Array parity is checked offline exhaustively
  and randomly; live array shadowing is not currently provided.

  Correctness checks: all 65,536 half encodings; boundary floats including NaNs,
  infinities, signed zeros and subnormals; 16,000 random tests across array
  overlap directions, matrix aliases, every input byte alignment, FP rounding
  modes, canaries, ABI state and unsupported-range fallbacks.
  Existing timing checks pass enabled, disabled and forced configurations.
  Existing resolve-arena preservation/overlap/bounds/fence checks pass.

  Function benchmark: exact guest ABI inputs with native dispatch included.
  Final dispatch-inclusive sample (ns/call):
    pack 1024 elements: 40069.50 original -> 474.37 native (84.5x)
    unpack 1024 elements: 17179.03 -> 266.42 (64.5x)
    normal transform: 8.75 -> 5.63 (1.55x)
    matrix transpose: 18.42 -> 6.55 (2.81x)
  Raw results: private/math-checks-observed.txt. Each iteration includes a
  compiler memory-observation barrier in both paths to retain every output. Host load and cache state affect
  absolute times; these numbers describe the tested buffers, not all sizes.
  These are CPU call timings, not GPU work or end-to-end frame speedups.

Measurement protocol
  Same executable, SDK/runtime, shader bundle, original saves/settings, and
  snapshot of warmed cache; original disables both native switches. Four runs
  in original/native/native/original order, 80 seconds each, sample 30..60 sec
  after first guest present. Frame cap 120, internal scale 1, fast precision,
  source output, film grain off, texture filtering off. No user input synthesized.
  Metal HUD enabled equally, validation and live shadow checks disabled.
  Discarded m1-original-sample: compilation overlapped that run.
  These boot/automatic-attract windows are exploratory, with no visual matching
  or identical-frame replay. They cannot establish a controlled gameplay FPS
  change or render parity. No whole CPU-frame critical path is measured; CPU
  values are the VdSwap-calling thread only.
  GPU time comes from Metal HUD's per-host-frame GPU-time pairs; whole HUD log
  batches are aligned approximately to guest-frame windows by wall time. Host
  presents and guest VdSwap calls may differ. Log format and metric definitions:
  https://developer.apple.com/documentation/xcode/monitoring-your-metal-apps-graphics-performance
  https://developer.apple.com/documentation/xcode/understanding-metal-performance-hud-metrics
  No change to GPU draw/dispatch algorithms was made by M1 or M2.

Regressions / unresolved evidence
  - Scalar transform parity/performance regression was repaired using ARM SIMD.
  - Restored-source timestamp issue was corrected and live entry counters verified.
  - No fatal, differential mismatch, or Metal API validation error was observed
    in final validation runs or any of the four sample runs.
  - The experiment does not demonstrate an FPS or GPU-work reduction. B1 had
    lower FPS and higher RSS than A1; B2 reversed those tendencies. Same-frame
    visual replay is still required to resolve frame/memory regressions.
  - Visual capture was unavailable. Interactive gameplay, Blade Mode,
    save/load behavior and concurrency under sustained gameplay remain unverified.
  - Whole-game rendering/memory/synchronization parity is not established by
    CPU differential tests or successful unattended runs.
  - All replacements remain isolated and switchable. No integration performed.

Classification
- CPU: no new verified critical-path or end-to-end improvement.
- GPU: redundant dump dispatches/tiles omitted, but no verified GPU frame-time
  gain; measured averages adverse. Both new GPU switches default0.
- Architecture: explicit native source coherence and write intent replace
  unconditional materialization; no direct Metal backend/shader replacement.

Fallbacks
MGR_NATIVE_RESOLVE=0: original GPU dumps (default).
MGR_NATIVE_RESOLVE=1 MGR_NATIVE_RESOLVE_WRITES=0: M4 conservative coherence.
MGR_NATIVE_RESOLVE=1 MGR_NATIVE_RESOLVE_WRITES=1: M5 selective invalidation.
MGR_NATIVE_MATH=0 MGR_NATIVE_MEMORY=0 retain previous guest-function fallbacks.
Do not enable the rendering candidates by default or integrate on these data.
